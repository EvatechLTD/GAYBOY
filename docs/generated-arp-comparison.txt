Question
Can the existing1/16 sequencer at240 BPM play the same music more cheaply
as Generate-written notes than a live1/32 arp at120 BPM?

Method
- 36 conditions: internal/link-master clocks x menu/sequencer pages x
  4/8/16 attacks per second x three implementations.
- A: live arp120 BPM, divisions1/8,1/16,1/32.
- B: live arp240 BPM, divisions1/4,1/8,1/16.
- C: production Generate ARP LINE at240 BPM, quarter/eighth/sixteenth rhythm.
- In B and C every other track has doubled event positions, durations and
  track lengths. Drum length16->32; Wave32->64. Accompaniment has the same
  intended wall-clock timing, pitches, velocities and gates; BPM alone is
  not used as an equal-workload shortcut.
- Generate controls use C major, ascending contour, no variation; invocation
  and APPLY execute the real ROM UI/Generate code, not a host-generated line.
- All three arms use the same C/E/G pitches and127 velocity.
- P2 phrase has eight intended attacks [C,E,G,C,E,G,C,E], then resets.
- At16Hz its loop lengths are4 steps at120 or8 steps at240. This intentionally
  tests a short looping arp; it is not an indefinitely held chord benchmark.
- Existing generator shape repeats over two meter-defined bars; meter was
  chosen per rate to produce this exact eight-note phrase.
- Three held events versus eight explicit events;19 versus24 total events.
- No timebase changes: the immutable pre-resolution build is hash-checked.
- User emulator/save are separate and untouched. Source meter prototype remains
  paused, unvalidated and unmerged.

CPU measurement
- Timed function entry/return hooks count emulated cycles, not host CPU time.
- Listed percentages sum disjoint EXCLUSIVE spans of instrumented audio/
  sequencer functions. They omit uninstrumented wrappers and audio polling
  checks inside UI functions; they are not complete system utilization.
- Audio is measured separately from a saved playback state with actual APU
  frequency/trigger writes. Buffered editor commits are included.
- Input latency measures queued edge acknowledgment, not finished drawing.
- Menu inputs move menu selection; grid inputs move the pitch cursor and
  can require redraws, so grid max delays include drawing work.

Failures and limits
- Explicit generated lines preserve the intended pitch order in all12 conditions.
- Some fastest short-loop live-arp runs repeat/skip the intended phrase position
  and have one-step-scale timing outliers. Thus these are matched INTENDED
  phrases, not36 successful identical audio traces. Slower traces are mostly
  exact; see raw pitch-order flags and interval outliers in the JSON.
- Live240 link-master start/release acknowledgment exceeded the6s bound in
  all three menu cases. Steady playback was measured afterward.
- Live240 link-master grid cases each had an input acknowledgment timeout.
- Remaining input delays depend heavily on chord-grid redraw versus menu.
- No real connected peer in link-master profiling; prior cable tests are
  separate evidence, not part of this benchmark.

Interpretation
- At the same240 BPM, generated explicit notes cost less than live arp in
  every measured context/rate.
- Against120 BPM live arp, Generate240 is cheaper on the sequencer page,
  where its note attacks use the edit-buffer IRQ path.
- In menu pages,120 BPM live arp is cheaper than Generate240: doubling
  scheduler step frequency outweighs the saved arp work in this fixture.
- Therefore keep meter and resolution decisions separate. Doubling BPM is
  musically workable after retiming every track, but not a universal CPU win.
- A natural next experiment is prepared single-note event playback across
  pages, avoiding a whole-pattern timebase change. This is a proposal only.
