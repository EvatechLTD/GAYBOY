LINKED MIXER: UI AND NATIVE LINK PROTOCOL PROPOSAL
2026-10-19 — Design proposal; no ROM behavior changed.

Objective
---------
One master mixer can operate both machines, with independently selectable
patterns and editable visibility/order. Timing, audio delivery, launch grids
and recovery take precedence over every remote feature. This extends GAYBOY
native mode only; LSDJ/ARDUINOBOY/PO/GATE retain their current behavior.

1. Mixer UI
-----------
Keep five visible strips and horizontal scrolling on the 160x144 screen.
Use a persistent top-level device selector: LOCAL / LINK / BOTH. LOCAL is
the current machine, LINK is the attached slave; BOTH concatenates the two
ordered strip lists. Mark every strip L or R so identical track names cannot
be confused. Do not interleave machines arbitrarily in the first version.

Suggested BOTH view (schematic, not final pixel art):

  MIXER       BOTH  >
  STOP  LAUNCH 1/1
  BPM 120  LINK OK
  L:P1 L:P2 L:DR R:P1 R:DR
    M    -    -    -    M
    -    S    -    -    -
       [five faders]
   LR   LR   LR    L    R
  PADS LOCAL      >
  [A01][A02][A04][A08]
  [three-character names]
  04 BREAK      A LAUNCH

Retain mute, solo, volume 0..127 and pan OFF/R/L/LR for each of the seven
main tracks. Preserve existing drum subvoice mute/solo strips, with the same
capabilities remotely. Do not imply per-subvoice volume/pan exists today.
Drum subvoices appear through an expandable DRM group and can be hidden
individually. Remote audio stays on the slave's audio output: the cable
carries control, not audio; combining outputs still needs an audio mixer.

PADS LOCAL / LINK switches the lower pad bank independently of the strips.
Each machine retains eight live pad slots; this is not a remote browser for
the entire sparse pattern library. Hidden pads compact into paged rows and
keep their original slot numbers. Focus shows the full cached 16-character
name in a detail view; compact pads keep three-character labels. Active,
queued, preparing, unavailable and unconfirmed states have distinct marks.
Remote B opens details, not the local pattern editor.

Add a visible SETUP entry in the mixer header. Inside SETUP:
  - LAYOUT: LOCAL/LINK tracks, drum subvoices and live pads.
  - A toggles visibility; explicit MOVE mode changes order with arrows.
  - SHOW ALL restores access; zero visible items shows a SETUP shortcut.
  - REFRESH LINK NAMES explicitly requests a new remote name snapshot.
  - FETCH WHILE STOPPED appears if live-transfer safety is not validated.

Hiding is presentation only. It never mutes, stops, unloads or changes a
pattern. Hidden active/queued pads and hidden audible tracks remain called
out in the header/detail view. No automatic hiding when a track is empty:
the next pattern may use it. Offer explicit user-selected visibility first.
Focus/scroll use logical device+track/slot IDs, never visible-array indices.
Layout editing does not borrow buttons used for live fader/pad actions.

Local and remote solo are scoped to their own machine. A remote solo does
not silently mute local tracks. A future cross-device solo would be an
explicit separate feature requiring coordinated state on both machines.

Remote controls show pending changes until the slave confirms authoritative
state. Coalesce rapid fader edits; do not enqueue every repeated key press.
Disconnect freezes controls and marks cached names/state STALE. Never apply
old queued edits automatically on reconnect. Local controls remain usable.

2. State, persistence and memory
--------------------------------
Separate MixerLayout (visibility/order), RemoteMirror (cached names/state),
and LinkSession (protocol state) from the existing audio-facing Mixer.
The layout belongs to the local project/song, not to individual patterns;
changing patterns must not restore an unrelated layout. Remote names/state
are volatile. Remote controls retain the slave's existing per-pattern mixer
semantics; acknowledge the resulting state after a pattern load.

Use seven-bit main-track and 13-bit drum visibility masks per machine,
eight-bit pad masks, and bounded order arrays. Keep stable device/track IDs.
Layout persistence needs a versioned optional record, checksum and atomic
commit consistent with sparse-store recovery. Missing/invalid records mean
the current all-visible layout. Do not overwrite legacy metadata or expand
fixed-address mx in place. Inspect the linker map and RAM ownership before
assigning storage: existing caches at ACC4/AE40/AE58 and B000 scratch are
already shared. Bank zero must remain selected whenever audio can run.

Budget initially: 128 bytes for eight 16-byte remote names, a validity mask,
bounded mixer/status mirrors, one small RX staging frame, one TX staging
frame and one outstanding reliable transaction per direction. Reserve exact
addresses only after map/stack review; no dynamic allocation, whole-library
cache, extra audio-buffer copies or cache rebuild on every clock. Incoming
name chunks update a staging slot; publish only validated complete records.
Whole-list revision changes mark the previous list stale until refresh ends.

3. Preserve the existing real-time plane
---------------------------------------
Keep the 24-bit oscillator, numbered 80..BF clocks, F1 tempo, FA/FB/FC
transport and F2 phase alignment semantics. Preserve slave local-launch
grid/remainder handling and the original PCM interrupt period. Do not add
division, rendering, storage, packet parsing or bank switching to IRQs.
Do not reinterpret F2 as a remote pad selection command.

Current code evidence:
  src/sync_clock.c: fixed-ROM oscillator and syncdue priority.
  src/main.c serial_isr: master discards SB input; slave rearms zero reply.
  src/sync.c: 32-byte TX ring, tempo/phase parser, bounded receive handling.
  src/mixer.c: seven main strips, 13 drum strips, eight live pads, five-wide
               rendering and incremental graphics caches.

Strict priority is necessary but insufficient. At 8192 bit/s one eight-bit
transfer occupies approximately 0.977 ms. At 300 BPM clocks are 8.333 ms
apart. Starting a background byte immediately before a due clock can delay
that clock for almost a millisecond. Never rely on average free bandwidth,
a FIFO priority flag, or the existing synctxwait cooldown as a safety proof.

4. Two-direction native extension
----------------------------------
The serial master remains the only clock source. The slave never initiates
a transfer. Every master transfer simultaneously shifts a slave reply byte.
Use existing clock transfers to carry slave replies: names/status can flow
back without adding transfers while playback is running. The reply must be
prepared before the transfer begins; assume at least one-transfer latency.

Minimal fixed-ROM ISR changes capture an eligible master RX byte and load
the slave's next precomputed reply byte. IRQs only move bytes/indices, rearm
serial and preserve existing due-clock priority. Parse in bounded foreground
service after sequencer/audio work. Measure the added cycles on both roles;
piggybacking avoids added wire time, not added CPU work.

Capability handshake is explicit when connecting remote controls. A legacy
slave returns zero/never completes HELLO, so retain clock-only operation and
disable remote actions. No automatic retries forever and no handshake bytes
in raw sync modes. An explicit name refresh may initiate this handshake.
Handshake establishes a fresh session token, protocol version and supported
track/control capabilities; every reconnect invalidates prior transactions.

Proposed reserved extension prefix: F3, subject to MIDI parser audit before
assignment. Everything following it is seven-bit clean:
  F3 | length | type | session[2] | request[2] | payload | crc7
Length counts type through CRC, bounded to 24 bytes. Session/request are
14-bit values, little-endian seven-bit groups. CRC-7 uses polynomial 0x09,
initial zero, MSB-first over length through payload (exact vectors required).
Arbitrary eight-bit masks split into seven-bit groups. Labels are printable
ASCII, 16 characters maximum, transported in bounded offset chunks.

Existing clock bytes may interleave between extension bytes and must always
be serviced immediately without consuming a packet position. Legacy tempo,
transport and phase prefixes abort an unfinished extension frame and run
their existing handling. The sender restarts an interrupted extension frame
from F3 with the same request ID; never resume orphan payload bytes. Malformed
length, checksum or a bounded timeout discards only extension state. While
an extension frame is open, its data must never leak to the MIDI parser.
Zero is an idle reply only outside a frame. F3 restarts a damaged frame.

Message families:
  HELLO / HELLO_ACK: version, capabilities, fresh session token.
  GET_NAMES / NAME_CHUNK / NAMES_DONE: request ID, bank revision, slot,
    offset, final length, bounded text. Only initiated by manual refresh.
  GET_STATE / STATE: active/queued/preparing pads, main levels/pans,
    mute/solo masks, drum masks, revision; split into bounded chunks.
  SET_MIX / RESULT: track ID, field, absolute value, expected pattern epoch.
  PREPARE_PAD / READY / COMMIT_PAD / RESULT: safe remote launch flow below.
  CANCEL / ERROR: terminate optional work without touching transport.

Slave-local edits publish a coalesced state revision, not names. Master
requests state deltas/snapshots at a bounded rate; never poll names. Changes
to remote names merely set NAMES STALE until the next manual refresh.
Refresh reads existing indexed pad names in bounded foreground work; never
force autosnapshot, scan event data or block audio for a complete bank read.

Use absolute SET values, not toggle commands. Duplicates replay the last
result without reapplying. Allow one reliable request outstanding per
direction, finite retries with backoff, and bounded timeout. Superseded
fader targets live in a fixed per-field desired-state table, outside the
transport queue. ACK means applied (or explicitly accepted for launch),
not merely received. On mismatch, stale epoch or disconnect, report current
state and require a fresh user action. Reserve response capacity for control
results; name transfer may yield, restart or be canceled.

5. Admission: optional traffic must never hold up clocks
--------------------------------------------------------
Master-to-slave commands need extra master transfers. Admission must prove
the entire byte can complete before the earliest possible next clock:
  conservative time-to-next-clock > byte duration + worst-case interrupt
  latency + foreground admission/start cost + measured safety margin.
Read oscillator phase/increment consistently in a short critical section,
account for timer quantization, active engine period and pending interrupt
flags, and recheck immediately at the serial start. Reject if serial busy,
clock due, start/stop/phase work pending, tempo/engine change invalidated the
estimate, or RX/service budgets lack capacity. Do not assume the foreground
will run again before the next clock. A late byte is dropped/deferred before
starting, never fixed by resetting an active serial transfer.

Keep extension scheduling outside sync_clock_isr. Model engine changes and
the very next timer firing: a phase estimate that ignores these is unsafe.
If the guard cannot be proven across an engine/configuration, disable extra
transfers while playing in that configuration. The feature waits; music
does not. Initial safe rollout may allow all requests only while stopped,
then permit live commands only after admission and cycle gates pass.

Stopped native master uses bounded low-rate polls to clock replies, with
no oscillator start or implicit transport action. Cancel polls before play
startup; an already active byte must complete through the existing serial
completion path. No retry loops or synchronous wait-for-response anywhere
in mixer input/render, transport or pattern preparation.

Separate optional traffic from the existing essential TX ring. Never fill
its 31 usable slots with names/remote commands. Bound extra bytes per clock
interval and total foreground work, with control results ahead of names.
If budgets are exhausted, optional work stalls. A stalled parser cannot
stall clock receive, extend critical sections or trigger transport reset.

6. Remote pattern launch and musical boundaries
-----------------------------------------------
Independent remote launches call the same preparation/handoff path as a
local slave launch. Preparation preserves the received-clock grid. Master
shows PREPARING, READY, QUEUED and the final authoritative active pad.

For a deliberately timed remote launch, PREPARE_PAD loads/prepares first.
Only after READY can COMMIT_PAD specify an agreed future boundary in a
shared transport epoch (extended clock counter anchored at explicit start,
plus subdivision/phase as needed). Modulo-64 clock numbers alone cannot
identify a future bar safely. Epoch/boundary handling needs a separate
validated extension; never repurpose the recovery counter or remainder.
Late/mismatched COMMIT is rejected and reported, never executed immediately.
The user may then explicitly queue the next boundary.

Independent local/remote launching is v1. Do not advertise atomic BOTH
launches: coordinating two machines without late preparation/ACK races is
additional work. Existing F2 master-launch alignment still resets the
slave's current pattern as today. Its interaction with a queued remote
launch must be specified and tested: process F2 first; invalidate/recompute
any target tied to the old pattern phase and report a missed target rather
than silently moving it. Transport stop/start cancels pending commits.

7. Failure and compatibility behavior
--------------------------------------
No cable/old ROM: local mixer and existing native clock continue unchanged.
Failed name refresh: retain old labels marked stale, permit explicit retry.
RX overflow: discard extension transaction and show remote fault; do not
reset oscillator, discard essential clocks or flood recovery requests.
Reconnect: new session, fresh state, explicit name refresh, no edit replay.
Invalid target/value: reject; never write unchecked indices into mixer RAM.
Sequence gaps: retain the existing numbered-clock recovery behavior.
Long ambiguous gaps are not repaired using remote names/state messages.
No hot-plug/rejoin synchronization promise beyond the existing native start
semantics until a separate recovery design has hardware evidence.

8. Implementation and acceptance gates
---------------------------------------
A. Visibility/order with no protocol change. Verify hide/show/focus, zero
   visible items, active hidden pads, persistence/recovery and render cost.
B. Test framing, capability negotiation and stopped-only name/state fetch.
C. Add piggyback replies and measure ISR/foreground cost before live fetch.
D. Implement/prove guarded live admission; enable per engine only on pass.
E. Remote absolute mixer edits; then preparation/remote boundary launches.

Before each timing-affecting stage, pin the exact current working-tree ROM,
symbols, compiler and build configuration, recording SHA256 and raw metrics.
The checkout already contains extensive local changes; do not replace them
with an older handoff ROM. The handoff cites a slave-launch results file
that is absent here, so establish a reproducible baseline from actual files.

Extend tools/test_sync_link.cjs using the real bit-level two-machine cable
core, not injected RX bytes. Cover 30/120/300 BPM, all engines, dense PCM,
rapid mixer edits, name refresh, rendering, storage, tempo/engine changes,
pad preparation, retriggers and Start-menu navigation. Randomize attempted
extension starts around every clock deadline; trace start/completion cycles
and prove no optional byte overlaps the earliest due-clock instant.

Compare baseline and extension under identical musical and UI workloads:
  - no additional clock-launch delay attributable to optional transfers;
  - no regression in drift, clock jitter distribution/max or note timing;
  - no increase in audio underruns/missed deadlines or UI latency;
  - no queue overflows, restarted active transfers or dropped clock bytes;
  - unchanged launch grid/remainder and recovery under equivalent faults;
  - bounded ISR cycles, stack usage and foreground work at maximum load.
The existing cable test's <4 ms jitter ceiling alone is insufficient:
remaining under that threshold can still hide a regression from baseline.
Run existing sync IRQ/audio budgets, slave-clock CPU/grid tests and slave
launch tests across all five modes; raw protocols must remain unaffected.

Inject truncation, invalid lengths/CRC, duplicates, slow consumer, lost ACKs,
disconnect at every frame position, reconnect and legacy-peer behavior.
Verify essential transport can interrupt a partial frame and remote commands
cannot reset timing. Hardware checks on actual supported consoles/cables
are required before claiming live-operation performance parity.

There is no honest architecture-only guarantee of zero extra CPU cost.
The enforceable contract is zero optional wire blocking of clock deadlines,
bounded work, measured performance parity and automatic refusal to send
optional traffic where those conditions cannot be met. Never trade clock
quality for faster name refresh or more responsive remote faders.
